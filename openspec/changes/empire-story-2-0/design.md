# Design

## Context

See proposal.md Why. Current state: turf takeovers settle in `block-war-settle.service.ts`, business flips in `business-action.service.ts`, coverage is manual via `admin-news.service.ts` -> `GameNews`, season memory is limited to `RoundAftermathReport` + `AccountCosmeticUnlock`. Web reads via `game.routes.ts` DTOs in `apps/server/src/game/dto.ts`.

Constraint: money is integer cents, round reset must stay clean, legacy must confer no power.

## Goals / Non-Goals

**Goals:**
- One `CityMemoryEvent` backbone all story features read from.
- Template-driven Daily with admin gate, no LLM dependency at launch.
- Operations reuse scout/crew/combat math, no new combat engine.
- Prototype gate after city-memory + one operation + Daily draft.

**Non-Goals:**
- No real-time co-op, no custom operation map editor.
- No procedural narrative generation, no player-written newspaper.
- No career-specific balance fork, no legacy power carryover.

## Decisions

- **Single event table over per-system feeds:** `CityMemoryEvent(roundId, cityId, kind, actorIds, summaryJson, visibility, idempotencyKey)` with unique key per source settle. Alternative was polling turf/war tables per consumer — rejected because consumers diverge and Daily/Black Book/Legacy need one truth.
- **Emit at settle time, render lazily:** emitters in settle services write event in same Prisma transaction as ownership change. Banners, faction shifts, heat read latest event. Alternative cron aggregation — rejected, causes stale banners.
- **Daily as draft queue:** generator job reads new public events -> `GameNews(draft, autoGenerated=true)` -> admin approve/edit in existing `AdminNewsPage.tsx`. Alternative direct publish — rejected, spam/abuse risk.
- **Operations as state machine, not script:** `Operation(status: intel/collecting -> crew_lock -> ready -> executing -> reported, rolesJson, invites)` + `OperationParticipant`. The prototype execution uses the existing deterministic rules primitives with role modifiers, then writes an outcome report row + memory event. Async invites use the existing activity notification path. A later operation template can compose the full raid/scout resolvers when its target semantics match them.
- **Black Book as view, not store:** `IntelRumor` rows are thin pointers to memory/scout events plus confidence/expiresAt. Corroboration upgrades confidence. No exact enemy numbers, only ranges.
- **Legacy snapshot at round close:** `LegacyEntry(accountId, sourceRoundId, kind, title, summaryJson, coverNewsId)` written by round-close job from memory + aftermath aggregates. Excluded from all round-start queries by construction (account-scoped, never joined into `RoundPlayer` init).
- **Careers + origin as quest content:** `PlayerCareer(accountId, career, historyJson)` + `QuestDefinition` chain for origin beats. No new engine; `GettingStarted.tsx` becomes 4-step runner over `PlayerQuest` + `PendingEncountersPanel`.

## Risks / Trade-offs

- [Daily spam from large wars] → coverage threshold + dedupe per event + admin reject; templates capped per cycle.
- [Intel noise / harassment] → involved-only visibility, expiry, no exact locations for offline players.
- [Operation invites stalling] → expiry timeout reopens the role; idempotent execute.
- [Migration weight] → new tables only, no alter of money/round tables; backfill script for last season optional, defaults to empty legacy.

## Migration Plan

1. Prisma migrate: add 6 tables, no data rewrite.
2. Deploy emitters with the migrated build; verify one takeover -> one event -> banner. No runtime `storyMemoryEnabled` flag was added in this slice.
3. Invoke the Daily generator only in draft mode; admin publishes the first stories.
4. Pin new rounds to `classic-og-v3.0-c` for the origin chain; older pinned rounds remain unchanged.
5. Rollback: stop Daily invocation and new 1.8-p rounds, and disable new routes at deployment level if needed. Additive tables remain intact.

## Open Questions

- Daily launch threshold is supported public event kinds, capped at 20 events per call by default (100 maximum); ranking/tunable top-N coverage remains future work.
- Operation roster size for prototype — default 3 roles (driver, enforcer, intel).
